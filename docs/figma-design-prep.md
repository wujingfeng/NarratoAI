# NarratoAI Figma 设计稿前置准备包

生成日期：2026-07-03

本文档用于在正式调用 Figma 生成设计稿之前，统一设计输入、页面范围、功能还原规则、组件清单和验收标准。目标是让 Figma 设计稿尽量一比一承接当前已梳理的产品原型和底层功能逻辑，避免只画视觉、不对应真实流程。

## 1. 设计目标

本次 Figma 设计的目标不是复刻当前 Streamlit WebUI 的外观，而是基于当前项目能力，生成一套面向 C 端用户的 Web 产品设计稿。

核心目标：

- 首页让用户先选择创作类型，不直接上传素材。
- 创作流程围绕“上传素材 -> 自动/精细模式 -> AI 生成 -> 结果导出”展开。
- 自动模式突出任务进度与结果。
- 精细模式按步骤让用户确认字幕、剧情理解、文案、剪辑脚本、配音字幕、合成导出。
- 配置项集中放到配置中心，不堆在创作首页。
- 我的作品、素材库、配置中心、失败态、空状态都需要完整承接。
- 每个页面都要能追溯到真实功能、底层服务或当前项目能力差异。

## 4. 信息架构

全局导航：

- 首页
- 我的作品
- 素材库
- 配置中心
- 帮助

页面归属：

- 首页只负责选择创作类型。
- 上传页属于具体创作类型。
- 生成中、待确认、已完成、失败、已取消都归入“我的作品”任务体系。
- 配置中心只放全局配置，不进入创作首屏。
- 素材库统一管理视频、字幕、背景音乐。

## 5. 用户主流程

### 5.1 自动模式

```text
首页选择类型
-> 上传素材
-> 选择自动模式
-> 创建任务
-> 生成中页面
-> 成片结果 / 失败详情
```

自动模式按类型区分后台步骤：

| 类型 | 后台步骤 |
| --- | --- |
| 影视解说 / 短剧解说 | 字幕处理 -> 剧情理解 -> 生成剧本 -> 生成配音 -> 合成视频 |
| 画面解说 | 画面分析 -> 生成文案 -> 剪辑脚本 -> 配音字幕 -> 合成导出 |
| 短剧混剪 | 字幕处理 -> 片段分析 -> 生成混剪脚本 -> 合成导出 |

### 5.2 精细模式

```text
首页选择类型
-> 上传素材
-> 选择精细模式
-> 字幕确认
-> 剧情/画面/片段分析
-> 解说文案或混剪脚本
-> 剪辑脚本
-> 配音字幕
-> 合成导出
-> 成片结果 / 失败详情
```

精细模式每一步都需要提供：

- 当前步骤状态。
- 上一步结果摘要。
- 当前可编辑内容。
- 重新生成 / 编辑 / 确认下一步。
- 返回我的作品。

## 7. 设计语言

基于 `docs/c-user-web-prototype/src/styles.css`，Figma 应使用这些基础风格。

### 7.1 字体

- 中文优先：PingFang SC、Noto Sans SC、Microsoft YaHei。
- 系统回退：system-ui、sans-serif。
- 字重层级：
  - 页面标题：700-850。
  - 卡片标题：650-760。
  - 正文：400-500。
  - 状态标签/按钮：700-800。

### 7.2 颜色

| 用途 | 颜色 |
| --- | --- |
| 主文本 | `#101116` |
| 次级文本 | `#686d7a` |
| 分割线 | `#e7e9ee` |
| 页面浅底 | `#f6f8fb` |
| 主色/主按钮 | `#ff2f35` |
| 主色深色 | `#d9131b` |
| 生成中/辅助强调 | `#08aaa6` |
| 完成状态 | `#22b86a` |
| 字幕重点色 | `#ffd431` |

### 7.3 布局原则

- 桌面端优先宽屏 Web，内容区最大宽度可参考 1440-1510。
- 顶部导航固定或半固定，当前页红色下划线。
- 任务型页面使用左侧步骤/中间主工作区/右侧摘要或操作区。
- 不使用大面积营销式 hero 承载核心工作流；首页可以有强视觉，但创作页应更偏工具化。
- 卡片圆角不宜过大，工具卡片建议 8-12px。
- 主操作按钮红色，次操作白底描边，状态色保持稳定。

## 9. 页面状态要求

每个核心页面至少要覆盖：

- 默认状态。
- 加载/处理中状态。
- 成功状态。
- 失败状态。
- 空数据状态。
- 配置缺失状态。

特别注意：

- 上传页需要展示“未配置 ASR / LLM / TTS 时”的提示入口。
- 生成中页面需要能展示取消任务。
- 精细模式页面需要展示“保存为待确认作品，稍后继续”。
- 失败详情页需要保留已上传素材和已完成步骤。
- 成片结果页需要有下载视频、导出剪映草稿、复制文案、查看脚本。

## 10. 与当前项目能力的边界

Figma 可以设计为目标 C 端体验，但这些地方需要标注“需要后续实现”：

| 功能 | 当前差异 |
| --- | --- |
| 作品管理 | 当前 Streamlit WebUI 缺少完整 C 端作品列表和持久化任务中心 |
| 素材库 | 当前主要依赖本地 `resource/` 目录，不是完整素材管理系统 |
| 每段独立配音 | 当前生成链路主要按脚本 OST 生成 TTS，需要确认每段独立音色的数据结构 |
| 精细模式持久化 | 当前更多依赖 session 和本地文件，目标体验需要任务级持久化 |
| 用户账号 | 当前开源版没有完整登录、用户空间和权限体系 |
| 配置中心 | 当前配置散布在 Streamlit 面板，目标体验需要重新组织 |

设计稿中可以表现这些能力，但注释里要说明它们属于目标产品形态，不代表当前代码已经完整实现。

## 12. 还原验收清单

生成 Figma 后，按这张清单验收：

- 是否覆盖四类创作类型。
- 首页是否只做类型选择，没有上传入口。
- 上传页是否按类型展示不同必填项。
- 是否同时体现自动模式和精细模式。
- 自动模式是否有步骤进度、取消任务、完成跳转、失败跳转。
- 精细模式是否覆盖字幕、分析、文案、脚本、配音字幕、合成导出。
- 剪辑脚本是否包含 OST=0/1/2 的视觉区分。
- 结果页是否包含视频下载、剪映草稿导出、文案和脚本查看。
- 配置中心是否覆盖模型、TTS、字幕、BGM、视频导出。
- 素材库是否覆盖视频、字幕、背景音乐。
- 是否有作品列表、作品详情、待确认、已完成、已取消、失败状态。
- 是否有空状态和失败详情。
- 页面文案是否偏工具操作，不是营销长文案。
- 视觉风格是否沿用红色主色、青绿色辅助色、白底工具化布局。
- 是否避免把当前代码不稳定支持的能力做成不可解释的核心功能。

## 14. 下一步建议

调用 Figma 之前，建议先做一次选择：

- 如果目标是快速看整体方向：先生成 D01-D17 + D27-D31，覆盖主流程和配置中心。
- 如果目标是一比一完整交付：生成 D01-D40，并在 Figma 里建立组件、变量和可点击原型。

当前更推荐先生成 D01-D17 + D27-D31，因为它们覆盖了 C 端产品的主链路、精细模式和配置中心，能最快验证整体产品体验。
